# Native Windows safe file movement

## Authority, evidence and bounded deliverable

The Product Owner authorized autonomous technical milestones for the existing local-privacy project. This is a safety correction, not new product scope. Source baseline `6a8cf710353cad3d4c34f80fe701a17642032cee`, branch `codex/local-privacy-mode`, active isolated `.worktrees/ai-smart-naming`. Root's Windows synthetic diagnostics actually returned 2 failures: the old EXDEV/shutil branch overwrote an occupied destination; replacing the source after its fingerprint check moved unapproved bytes with success. Raw evidence remains private. Main `4feb712` and user shortcut are preserved.

Deliverable: independently tested `src/core/safe_file_move.py` and its native tests. It is deliberately not wired into RenameExecutor in this first milestone; the two old-engine defects are not closed until a separate integration milestone changes the production engine and re-verifies its callers.

## Choice and alternatives

Selected after the Product Owner's explicit cross-volume decision: held native source/ancestor handles and non-replacing by-handle SAME-VOLUME rename only. This binds mutation to actual opened objects rather than rechecking paths and then acting on them. Cross-volume automatic movement is explicitly refused with the original retained. No copy-only substitution, candidate publication, source deletion, or fallback to the unsafe old engine. Cross-volume support may return only after a separately approved and physically verified safe design.

Not selected: more exists/stat checks around shutil.move (still a mutation window and destination overwrite); CopyFileEx by pathname without owned handle publication/cleanup; copying while deleting an object whose other streams can still change. The Product Owner chose an explicit temporary cross-volume restriction over copy-only behavior or further delaying this milestone. No new permissions, ACL changes, firewall changes or elevated file access are used. Existing processing_intent_store is a fully read reference for native handles, not imported or edited: its replacement-enabled configuration writer is unsuitable for user files.

## Pure API

`safe_move(source: str, destination: str, *, expected_fingerprint: SourceFingerprint, allowed_roots: tuple[str, ...], create_parents: bool = True) -> SafeFileMoveResult` is worker-only synchronous I/O. No Qt imports, spawned threads, history, model/provider calls, user-data settings or callbacks. A private lock serializes native transactions; it creates no worker. Frozen result fields: `success: bool`, `new_path: str`, `error_code: str`, `recovery_required: bool`, `source_fingerprint: SourceFingerprint | None`, `owned_residue_paths: tuple[str, ...]`.

Success requires the same approved object is renamed to the exact same-volume destination, original bytes/size/mtime retained, and native completion/checked closes proven. It supplies destination and captured fingerprint with empty error/residue. Ordinary rejection performs no source mutation, has false success, empty new_path/residue and fixed error key. Cross-volume rejection uses SAFE_MOVE_CROSS_VOLUME_BLOCKED, false recovery_required and the admitted captured fingerprint; source remains at its original path. Uncertain post-mutation completion/close is false success plus recovery_required, known source/destination paths and a fixed recovery key, never ordinary success or invented rollback. All returned strings originate from approved paths or fixed bounded keys, never raw exceptions. Input failures perform zero native I/O.

Inputs are exact types: strings with bounded length <=4096, absolute local drive paths, no NUL/control characters, traversal components, device/UNC/extended-device syntax, alternate-stream syntax, trailing dot/space or reserved device components. Destination has a legal single basename with <=255 UTF-16 code units. Roots are an exact nonempty tuple of <=2000 unique bounded paths; fingerprints are exact SourceFingerprint with non-bool integer size/mtime >=0; create_parents is exact bool. Both paths must be lexically inside approved normalized roots; the selected authorizing roots must already exist and must not be created. Unused roots are syntax-validated but grant no authority outside the selected paths. Unsupported platform fails closed, without a path-only move fallback. Same source/destination is rejected, not an implicit rename/counter.

## Native transaction

1. Validate pure graph and containment. Open only the local drive anchor by absolute path. Acquire every later single component, including the source basename, relative to its retained parent with NtCreateFile, OBJ_DONT_REPARSE and FILE_OPEN_REPARSE_POINT; verify held directory/non-reparse attributes before descent. Directory handles request LIST_DIRECTORY, READ_ATTRIBUTES and SYNCHRONIZE, with FILE_SHARE_READ | FILE_SHARE_WRITE and no DELETE sharing. The actual R4 share-read-only run denied ordinary same-volume publication with sharing violation32; preserve that failed compatibility evidence. The actual 0x80/0x81 comparison established rename resistance, NOT a complete reparse barrier. Attribute access is exempt from share-mode enforcement: the retained FILE_WRITE_ATTRIBUTES witness actually converted a pinned empty directory. Protection therefore requires the verified relative traversal and nonempty guards below, not a share-mask-only containment guarantee. No reparse-following pathname reopen or CreateDirectoryW descendant creation remains. Open the source with read/attributes/DELETE rights and no sharing; verify the held regular file's identity and approved size/mtime before target mutation. These are ordinary rights, not ACL/privilege changes; inability to obtain them fails closed.
2. Pin/verify the existing selected target authorizing root WITHOUT creating descendants or guard files and compare its actual held volume to the admitted source. Cross-volume requests return the explicit blocked result BEFORE creating anything. Comparing drive-letter strings is not a volume check. Same-volume mutation additionally requires the held volume to report NTFS, because nonempty-directory reparse prevention is a required filesystem property in this milestone; an unsupported filesystem is refused, never treated as proven. Missing descendants are create-only, single-component, held-parent-relative native creations that obtain their handles together. Existing roots must not be created. Empty approved same-volume descendant directories may remain after a later failure; user file data must not be changed. Proven terminal normal exits release held handles with checked closes. Unresolved native completion/close is the explicit process-lifetime quarantine exception below, never a claim of completed cleanup.
3. Protect vulnerable directories with exclusively held, zero-content, create-only `.xuxia-move-` guard files created relative to their exact held parent and marked FILE_DELETE_ON_CLOSE. Guards may be created only inside selected approved roots after fingerprint and same-volume admission, never in a bare drive anchor or an unselected ancestor/system directory. A request requiring a guard in a bare drive anchor is refused without source mutation; choosing a drive root does not silently grant such guard creation. Keep a parent nonempty before creating its missing child; once that exact child is held without delete sharing, its presence replaces the intermediate guard. Retain source-parent and final-target-parent guards through publication and identity verification, so moving the source cannot expose a newly empty parent. Recheck parent metadata after guard acquisition; if a pre-guard mutation occurred, reject without source mutation. Guard insertion must first be physically shown not to redirect through a converted held parent. Guard-name collisions refuse without opening/deleting the pre-existing object. Guard contents are always empty; no user file/stream is copied. Checked handle close is the only guard cleanup, never path-based unlink. Additional directory metadata changes from owned guard creation/removal are an explicit limitation. Normal exits leave no guard files. On uncertainty, report bounded possible owned guard paths alongside source/destination (at most four paths with at most two live guards); do not claim the paths exist or that cleanup completed.
4. Compare held source and target-parent volume identities. Same volume: NtSetInformationFile(FileRenameInformation, class10) on the exact held source, ReplaceIfExists false, destination-parent RootDirectory handle plus relative basename. Use typed pointer-width IO_STATUS_BLOCK and NTSTATUS, check actual synchronous completion; STATUS_PENDING or unknown completion never implies success. Occupied destinations are refused atomically; no exists-then-overwriting rename. Preserve original bytes/metadata. No collision counter in this primitive.
5. There is NO cross-volume copying or source-disposition algorithm in this selected implementation. Remove the rejected copy/publication/delete branch and its unused copy/stream-enumeration/disposition helpers, rather than leaving an easily re-enabled unsafe path. No ReadFile/WriteFile/SetFileTime/FlushFileBuffers/source-delete call is needed by this rename-only primitive. Same-volume renamed objects retain their native streams/hardlink identity; this is not a claim of reconstructing metadata by copying it.
6. Same-volume rename-then-exception returns honest recovery and source/destination evidence. Handle-close failures and actual final cleanup must be checked; never suppress them into success. The R1 process-lifetime ownership correction remains binding. No path-based rollback, unlink after handle release, or silent old-engine fallback.

Same-parent/overlap ownership: reuse one guard per held directory; retain=True is sticky and takes priority over intermediate release. Creating a pinned child must not release the retained source-parent guard. Guard close and guard disappearance are separate facts: after a successful close, use only its still-owned parent and relative exact name to prove the directory entry is absent, never probe the closed numeric handle. An allowed external attribute handle can delay DELETE_ON_CLOSE; remaining/delete-pending/uncertain entries stop further operations and return recovery with possible guard residue, not false normal success. This check does not delete or overwrite a newly inserted foreign object. Physical normal-exit tests must independently verify no guard remains.

An existing legitimate directory write handle need not be denied by admission. Test both independent outcomes: while the owned guard is retained, a conversion attempt must not establish a junction or redirect output; a conversion before guard acquisition must cause an honest source-preserving refusal and no escaped guard/child/file. Retain the obsolete share-read-only writable-admission failure as historical evidence, not as the selected acceptance rule. Every generated guard path must also satisfy the <=4096 input-path bound before native submission.

Native compatibility correction: the actual Windows single-variable comparison used the same exclusive source, pinned parent and aligned relative UTF-16 buffer. SetFileInformationByHandle(FileRenameInfo) returned Win32 87; NtSetInformationFile(FileRenameInformation) returned NTSTATUS0 and IO_STATUS_BLOCK.Status0. Checked closes then showed source absent and non-BMP destination bytes/fingerprint preserved. This authorizes changing the user-mode native entry only, not a path-based fallback, security permission change or whole-transaction PASS. The original 19-failure run stays retained. No direct syscall numbers, kernel driver or privilege bypass is used; an unavailable native entry fails closed.

The fingerprint remains the existing size/mtime contract, not a cryptographic proof against a deliberate equal-size/equal-time forgery before handle admission. Holding the default stream prevents its replacement/write but does not freeze all NTFS streams. Root's actual late-ADS diagnostic demonstrated stream loss despite unchanged default-stream fingerprint: the source was deleted and the destination had only its default stream. The approved correction is now explicit cross-volume refusal, not a second stream query or a claim that the unsafe copying algorithm became safe. No cross-volume power-loss atomicity or metadata reconstruction is claimed. Production integration/recovery must preserve these limits; a new primitive alone does not settle historical Undo identity.

## Native uncertainty correction: bounded process-lifetime ownership

The independent review rejected freeing potentially pending request buffers and clearing ownership after a failed close. R1 corrected these within the same two-file milestone; its approval did not resolve ADS loss. Preserve that correction while separately implementing R2's approved refusal above. Keep the public signature and frozen result unchanged. At most one native transaction is active; at most one uncertain transaction is quarantined. A quarantined transaction blocks every later valid move before native file I/O with the fixed recovery key, with no new request incorrectly inheriting another transaction's residue paths. Invalid pure inputs still receive the fixed invalid-input result.

Allocate typed IOSB and the aligned UTF-16 rename buffer in one bounded, zero-initialized process-heap allocation. Ctypes views do not own its storage. Register ownership before submission. Explicitly free once only after proven completion; no finalizer or interpreter-exit free. A definitive negative nonpending Nt return is a rejected/terminal call, not a pending request merely because IOSB is unwritten. Unknown informational returns, success/IOSB inconsistency, or an exception after submission remain uncertain. On STATUS_PENDING perform one 250ms wait and inspect both its return and terminal IOSB: timeout, WAIT_FAILED, sentinel, pending or unknown IOSB never establishes completion. Even a subsequently terminal pending request never returns success; conservatively retain its allocation and all transaction handles for process lifetime. The finite wait does not promise a deadline for other synchronous native calls.

Apply the same ownership rule to relative creation: typed output-handle slot, IOSB, OBJECT_ATTRIBUTES, UNICODE_STRING and UTF-16 name live in bounded explicitly owned native storage, registered before NtCreateFile. Register a proven returned handle before freeing that storage. Negative nonpending results are terminal only when they did not return an unexplained handle; success requires valid output handle, exact status0/IOSB0 and the requested OPENED/CREATED information. Pending, informational, inconsistent, after-submission exception or ambiguous free quarantines all pointed-to storage and any returned handle; there is no retry or invented completion. Guard close/removal ambiguity also quarantines ownership.

On uncertainty transfer ownership before normal cleanup and do not dispose, close, roll back or free potentially involved native resources. On the first ambiguous close/free, preserve the original ownership record and stop further cleanup. Never retry, query or probe a possibly reused numeric handle/pointer. There is no quarantine-reset/retry API. The release boundary is actual OS process termination/restart, not GC, module reload or embedded-interpreter restart; those unsupported mechanisms must not be used as recovery. A restart releases still-open process resources but does not reverse physical moves/deletions, so surviving path evidence remains necessary. No forced exit, GC suppression, background cancellation or security mutation is added.

Verify controlled unresolved cases in owned subprocesses. Parent witnesses real sharing locks while the child is alive, permits a normal child exit, waits for actual process completion, then reopens/checks bytes and cleans only its exact owned fixtures. Tests must not rescue a forgotten production handle themselves. Pending responses remain explicitly controlled faults, not claims that native pending I/O actually occurred on this host.
